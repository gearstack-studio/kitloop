# Episode 5 GCP release tooling

These scripts prepare `lab-5-cloud-deployment-514310` in `asia-southeast1` for a **single** KitLoop Cloud Run service. Run them in Google Cloud Shell from a clean clone of the reviewed feature branch. Nothing here runs automatically. `preflight.sh` and `verify.sh` are read-only; each state-changing `prepare.sh` or `release.sh` action requires a matching typed confirmation. Stop on any error.

## Cost and permission gate

Before any `prepare.sh` or `release.sh` command, verify the active billing account, remaining Free Trial credits, budget alerts, regional quotas, and a current [pricing-calculator](https://cloud.google.com/products/calculator) estimate. An active billing account does not mean a resource is free. Cloud SQL runs continuously and may charge for compute, storage, backups, and network use. Cloud Run, Cloud Build, Artifact Registry, Secret Manager, logs, and VPC traffic may also charge. The [30-day Cloud SQL trial instance](https://docs.cloud.google.com/sql/docs/postgres/free-trial-instance) requires a new project, uses a fixed large configuration, lacks ordinary backups and an SLA, and can stop after its trial period. Eligibility of this existing lab project has not been established. The proposed paid `db-f1-micro` is a low-cost lab starting point, also without an SLA; increase it only after measuring resource use. No cloud resource has been created by this repository change.

The operator needs permission to enable APIs, administer the named Cloud SQL instance and VPC, create the repository and secrets, manage service accounts and their IAM bindings, submit Cloud Builds, and deploy Cloud Run services/jobs. Grant the operator `roles/iam.serviceAccountUser` on the four dedicated service accounts. Runtime and migration identities receive Cloud SQL Client and only their required secret access. The bootstrap identity receives temporary Cloud SQL and manifest access, revoked after provisioning; the runtime and migration identities never receive the manifest. The build identity receives Artifact Registry Writer on this repository and Logs Writer. Review actual IAM grants in Console before proceeding; these scripts never create service account keys. See [Cloud Run deployment permissions](https://docs.cloud.google.com/run/docs/reference/iam/roles) and [Secret Manager IAM](https://docs.cloud.google.com/secret-manager/docs/access-control).

## Integrated PR A runtime contract

Cloud Build uploads source to a dedicated private Cloud Storage bucket. This bucket can incur storage charges; its lifecycle removes staged source objects after seven days and soft delete is disabled. The build identity receives object read access on this bucket only, while the operator needs permission to create the bucket and upload source objects.

PR #32 is merged into staging and into this branch. The release commands use its production image and separate migration entrypoint:

| Contract | Required implementation |
| --- | --- |
| App image | Dockerfile target `production`, immutable tag `kitloop-app:<source SHA prefix>`, React SPA and Express `/api` on one origin, listening on `0.0.0.0:$PORT` (Cloud Run sends port 8080). Build with `VITE_API_BASE_URL=`. |
| Migration image | Dockerfile target `migration`, immutable tag `kitloop-migration:<source SHA prefix>`, containing Prisma CLI and checked-in migrations. Its default `node scripts/migrate.mjs` entrypoint reports a sanitized failure and exits nonzero; the Cloud Run job resets any previous command override. No seed runs. |
| Bootstrap | Explicit `node dist/bootstrap-cli.js` in the `production` image, supplied with `DATABASE_URL` and the reviewed `BOOTSTRAP_INPUT` JSON manifest from Secret Manager. It provisions accounts, assets and assignments transactionally; matching existing passwords and records are preserved. The one-time job uses its own service account and zero retries. |
| Runtime variables | `NODE_ENV=production`, `PORT` from Cloud Run, `APP_ORIGIN` set to the canonical HTTPS URL, `SESSION_TTL_HOURS=12`, `DATABASE_URL` and `SESSION_CSRF_SECRET` from Secret Manager. No `DEMO_*` or server secrets in `VITE_*` values. |
| Cloud SQL | Cloud SQL PostgreSQL 17, **private IP only**. Service and jobs use the same Cloud SQL attachment and VPC/subnet. The Prisma URL uses a percent-encoded `host=/cloudsql/PROJECT:REGION:INSTANCE` query value with `connection_limit=5`. The Cloud SQL connector provides authenticated encrypted connections. |
| HTTP and auth | `/` serves the app, `/api/health` returns 200, `/api/ready` returns 200 only when PostgreSQL is reachable and 503 otherwise. `Secure`, `HttpOnly`, `SameSite=Lax` cookie; same-origin API requests; Origin and CSRF validation remain enabled. |

Cloud Run cannot use the Compose hostname `api` or deploy the two Compose services as one container. The existing Nginx image remains for local Compose. PR B does not edit DEV4952's runtime implementation.

## Ordered Cloud Shell runbook

1. Clone the reviewed, **pushed** commit of `feat/5-first-gcp-deployment` (or, after merge, `sprint-1-staging`) and confirm `git status --porcelain` is empty. `release.sh build` refuses other branches, dirty trees and commits that are not on the matching `origin/` branch. Record the full source SHA.
2. Run `gcloud config set project lab-5-cloud-deployment-514310`, then `bash infra/gcp/preflight.sh`. Review billing, budgets, trial status, quota and prices manually. Obtain explicit approval for resource and IAM creation. Use `set -e` in the Cloud Shell release session so a failed step stops the sequence.
3. Run `bash infra/gcp/prepare.sh apis`, then `registry`, `identity` and `build-source`. Required APIs: Cloud Run, Artifact Registry, Cloud Build, Cloud Storage, Cloud SQL Admin, Secret Manager, IAM, Compute Engine, Service Networking, and Cloud Logging. The source bucket is private, uses uniform bucket access, and has a seven-day object lifecycle.
4. Check all project, peered, and organization IP ranges. Choose a non-overlapping Cloud Run subnet CIDR (at least `/26` is prudent for Direct VPC egress) and a private-service-access range. Run `bash infra/gcp/prepare.sh network SUBNET_CIDR PSA_BASE_IP PSA_PREFIX`. This creates a dedicated VPC, subnet, allocated range and private services access. On partial failure, inspect resources before retrying; the script will not delete or overwrite them.
5. After cost approval, run `bash infra/gcp/prepare.sh database`. It creates a zonal Enterprise PostgreSQL 17 `db-f1-micro`, private IP only, 10 GiB SSD, storage growth capped at 20 GiB, scheduled backups, and deletion protection. Confirm the instance is `RUNNABLE` before proceeding.
6. Run `bash infra/gcp/prepare.sh secrets`. It generates random database and CSRF credentials, creates the `kitloop_app` SQL user, and stores the Prisma socket URL and CSRF key as regional Secret Manager versions. Output contains names only. The SQL user password briefly appears as a process argument to `gcloud`; use a trusted Cloud Shell session and never run with shell tracing. An interrupted run may be partially provisioned; inspect before retrying rather than rotating blindly.
7. Run `bash infra/gcp/prepare.sh grants`. Confirm the build service account can read the dedicated source bucket, write to Artifact Registry, and write Cloud Logging. Confirm the operator can upload build source to that bucket. No default compute service account is used for the app.
8. Run `bash infra/gcp/release.sh build`. It submits Cloud Build (30-minute timeout), builds both PR A targets, pushes both images, and prints the full source SHA and immutable image digests. Record the Cloud Build ID and success status from its output; do not claim success until it completes. Cloud Build and Artifact Registry both need their own quota and IAM checks.
9. Review migrations and backup state. Run `bash infra/gcp/release.sh migrate SHA`, using the 12-character source SHA prefix. It deploys and executes the migration image's default entrypoint with zero retries, waits for completion and checks the latest execution against the expected digest. A failed, incomplete or mismatched execution stops bootstrap and deployment. Record the execution ID and result. Never run `db:migrate` or the demo seed on production.
10. **First release only.** Prepare a reviewed `BOOTSTRAP_INPUT` JSON manifest following `server/.env.production.example` in a mode-0600 file **outside the repository**. Supply account passwords from the team password manager; never put the manifest in shell history or source control. Run `bash infra/gcp/prepare.sh bootstrap-secrets /absolute/path/to/reviewed-bootstrap.json`, then `bootstrap-grants` and `bash infra/gcp/release.sh bootstrap SHA`. After verifying the execution, the script records its name as the Cloud SQL instance label `kitloop_bootstrap`. Verify account/asset counts without credentials, then run `bootstrap-revoke`. You may then delete the one-time job after retaining redacted execution evidence: deployment reads the label, not the job. The runtime and migration service accounts never receive manifest access.
11. Run `bash infra/gcp/release.sh deploy SHA`. Every deploy requires a successful migration execution of this commit's migration digest and the recorded bootstrap label. `APP_ORIGIN` is always the canonical URL (below), so no revision uses a placeholder origin.
    - **First deployment** (no `kitloop` service yet): creates a **private** service (`--no-allow-unauthenticated`) with Direct VPC egress and Cloud SQL attachment. Cloud Run routes a new service's first revision immediately; nobody can invoke it until `publish`.
    - **Later releases**: deploys the new revision with `--no-traffic` and tag `candidate`, checks `/`, `/api/health` and `/api/ready` on the candidate URL with an identity token, and only then routes 100% of traffic to it. Invoker IAM is never changed, so a public service stays public; the script stops if access changes. If the candidate fails, traffic stays on the previous revision.
12. After the first deployment, run `bash infra/gcp/verify.sh private`. It reports the revision(s) actually receiving traffic and rejects any serving revision without the canonical `APP_ORIGIN`. Then, after approval to publish, run `bash infra/gcp/release.sh publish`. This checks the private service, grants public invoke, and checks public HTTP endpoints.
13. In a browser, use the uniquely provisioned accounts to test login, session restoration after refresh, catalog read, borrow request, custodian checkout, and persistence across a new revision. Record statuses, counts, and redacted screenshots only. The automated HTTP check does not establish these browser results.

For a later release, repeat steps 8, 9 and 11 for the new commit. Bootstrap and `publish` are not repeated.

**Canonical URL.** The only supported browser origin is Cloud Run's deterministic URL `https://kitloop-PROJECT_NUMBER.asia-southeast1.run.app`, computed from the project number before the service exists. Cloud Run also serves a legacy `https://kitloop-HASH-as.a.run.app` URL and a `candidate---` tag URL; logins and other state-changing requests from those origins are rejected by the Origin/CSRF check. The scripts stop if Cloud Run does not report the canonical URL for the service.

**Zero-downtime limits.** A later release switches traffic only after the candidate passes, and Cloud Run drains in-flight requests on the old revision. This is not a full guarantee: `migrate` runs while the previous revision still serves, so migrations must be backward compatible; the HTTP checks do not exercise login or writes on the candidate; and a cold start may slow the first requests after the switch.

**Bootstrap record.** The `kitloop_bootstrap` label belongs to the Cloud SQL instance whose database was provisioned. A recreated instance has no label and requires bootstrap again. If the database is ever reset inside the same instance, remove the label first (`gcloud sql instances patch kitloop-pg --remove-labels=kitloop_bootstrap`). The operator needs permission to update instance labels.

For rollback, run `bash infra/gcp/release.sh rollback REVISION` with a previous revision name from `verify.sh` output or `gcloud run revisions list`. It accepts only a ready `kitloop` revision running an Artifact Registry digest with the canonical `APP_ORIGIN`, routes 100% of traffic to it, confirms that routing, and reruns the HTTP checks for the current public or private state. The next `release.sh deploy` moves traffic to its new revision after checks. Rollback **does not** undo a database migration. Keep migrations backward compatible with the preceding app revision; use a reviewed restore plan if data repair is required. First deployment has no earlier revision to roll back to.

## Evidence and troubleshooting

Record the source SHA, Cloud Build ID/status, two image digests, Cloud SQL instance state and private connection name, migration and bootstrap execution IDs/statuses, Cloud Run revision and HTTPS URL, `/`, `/api/health`, `/api/ready` HTTP statuses, browser workflow, persistence after revision replacement, backup setting, IAM review, cost/budget check, and any failed step. Keep evidence under `docs/labs/lab-05/` or the PR, with no expanded Compose config, database URL, manifest, passwords, access tokens, cookies, CSRF headers, or raw secret values. If readiness fails, inspect Cloud Run revision logs and migration status before publishing. If a build fails, retain the Cloud Build ID and inspect its step logs. Do not retry migration blindly after partial success.
