# Episode 5 GCP release tooling

These scripts prepare `lab-5-cloud-deployment-514310` in `asia-southeast1` for a **single** KitLoop Cloud Run service. Run them in Google Cloud Shell from a clean clone of the reviewed feature branch. Nothing here runs automatically. `preflight.sh` and `verify.sh` are read-only; each state-changing `prepare.sh` or `release.sh` action requires a matching typed confirmation. Stop on any error.

## Cost and permission gate

Before any `prepare.sh` or `release.sh` command, verify the active billing account, remaining Free Trial credits, budget alerts, regional quotas, and a current [pricing-calculator](https://cloud.google.com/products/calculator) estimate. An active billing account does not mean a resource is free. Cloud SQL runs continuously and may charge for compute, storage, backups, and network use. Cloud Run, Cloud Build, Artifact Registry, Secret Manager, logs, and VPC traffic may also charge. The [30-day Cloud SQL trial instance](https://docs.cloud.google.com/sql/docs/postgres/free-trial-instance) requires a new project, uses a fixed large configuration, lacks ordinary backups and an SLA, and can stop after its trial period. Eligibility of this existing lab project has not been established. The proposed paid `db-f1-micro` is a low-cost lab starting point, also without an SLA; increase it only after measuring resource use. No cloud resource has been created by this repository change.

The operator needs permission to enable APIs, administer the named Cloud SQL instance and VPC, create the repository and secrets, manage service accounts and their IAM bindings, submit Cloud Builds, and deploy Cloud Run services/jobs. Grant the operator `roles/iam.serviceAccountUser` on the three dedicated service accounts. The runtime and migration identities receive Cloud SQL Client and only the secret access they need. The build identity receives Artifact Registry Writer on this repository and Logs Writer. Review actual IAM grants in Console before proceeding; these scripts never create service account keys. See [Cloud Run deployment permissions](https://docs.cloud.google.com/run/docs/reference/iam/roles) and [Secret Manager IAM](https://docs.cloud.google.com/secret-manager/docs/access-control).

## Contract with DEV4952

The release commands deliberately fail until the following production implementation exists and has passed its own tests:

| Contract | Required implementation |
| --- | --- |
| App image | Dockerfile target `cloud`, immutable tag `kitloop-app:<source SHA prefix>`, React SPA and Express `/api` on one origin, listening on `0.0.0.0:$PORT` (Cloud Run sends port 8080). Build with `VITE_API_BASE_URL=`. |
| Migration image | Dockerfile target `migrator`, immutable tag `kitloop-migrator:<source SHA prefix>`, containing Prisma CLI and checked-in migrations. Working directory must be `server/`; `npm run db:deploy` must exit nonzero on failure. No seed in the migration command. |
| Bootstrap | A separate, reviewed `npm run db:bootstrap` command in the `migrator` image. It receives `BOOTSTRAP_BORROWER_USERNAME=borrower.lab`, `BOOTSTRAP_CUSTODIAN_USERNAME=custodian.lab`, and two passwords from Secret Manager. It provisions accounts, assets, and assignments; must never call or weaken `db:seed`, log credentials, or reset an existing account on rerun. The job script refuses to run until this command exists. Provision before public access. |
| Runtime variables | `NODE_ENV=production`, `PORT` from Cloud Run, exact HTTPS `APP_ORIGIN`, `SESSION_TTL_HOURS=12`, `DATABASE_URL` and `SESSION_CSRF_SECRET` from Secret Manager. No `DEMO_*` or server secrets in `VITE_*` values. |
| Cloud SQL | Cloud SQL PostgreSQL 17, **private IP only**. Both service and job use the same Cloud SQL attachment and VPC/subnet. Prisma URL uses `host=/cloudsql/PROJECT:REGION:INSTANCE` with `connection_limit=5`. The Cloud SQL connector provides authenticated encrypted connections. |
| HTTP and auth | `/` serves the app, `/api/health` returns 200, `/api/ready` returns 200 only when PostgreSQL is reachable and 503 otherwise. `Secure`, `HttpOnly`, `SameSite=Lax` cookie; same-origin API requests; Origin and CSRF validation remain enabled. |

Cloud Run cannot use the Compose hostname `api` or deploy the two Compose services as one container. The existing Nginx image remains for local Compose. The release scripts do not edit DEV4952's implementation.

## Ordered Cloud Shell runbook

1. Clone the reviewed `feat/5-first-gcp-deployment` commit and confirm `git status --porcelain` is empty. Do not build from a dirty tree. Record the full source SHA.
2. Run `gcloud config set project lab-5-cloud-deployment-514310`, then `bash infra/gcp/preflight.sh`. Review billing, budgets, trial status, quota and prices manually. Obtain explicit approval for resource and IAM creation.
3. Run `bash infra/gcp/prepare.sh apis`, then `registry` and `identity`. Required APIs: Cloud Run, Artifact Registry, Cloud Build, Cloud SQL Admin, Secret Manager, IAM, Compute Engine, Service Networking, and Cloud Logging.
4. Check all project, peered, and organization IP ranges. Choose a non-overlapping Cloud Run subnet CIDR (at least `/26` is prudent for Direct VPC egress) and a private-service-access range. Run `bash infra/gcp/prepare.sh network SUBNET_CIDR PSA_BASE_IP PSA_PREFIX`. This creates a dedicated VPC, subnet, allocated range and private services access. On partial failure, inspect resources before retrying; the script will not delete or overwrite them.
5. After cost approval, run `bash infra/gcp/prepare.sh database`. It creates a zonal Enterprise PostgreSQL 17 `db-f1-micro`, private IP only, 10 GiB SSD, storage growth capped at 20 GiB, scheduled backups, and deletion protection. Confirm the instance is `RUNNABLE` before proceeding.
6. Run `bash infra/gcp/prepare.sh secrets`. It generates random database and CSRF credentials, creates the `kitloop_app` SQL user, and stores the Prisma socket URL and CSRF key as regional Secret Manager versions. Output contains names only. The SQL user password briefly appears as a process argument to `gcloud`; use a trusted Cloud Shell session and never run with shell tracing. An interrupted run may be partially provisioned; inspect before retrying rather than rotating blindly.
7. Run `bash infra/gcp/prepare.sh grants`. Confirm the build service account can write to the repository and Cloud Logging. No default compute service account is used for the app.
8. After DEV4952's image targets are integrated and tested, run `bash infra/gcp/release.sh build` from the clean feature branch. It submits Cloud Build, builds both targets, pushes both images, and prints the full source SHA and immutable image digests. Record the Cloud Build ID and success status from its output; do not claim success until it completes. Cloud Build and Artifact Registry both need their own quota and IAM checks.
9. Review migrations and backup state. Run `bash infra/gcp/release.sh migrate SHA`, using the 12-character source SHA prefix. It deploys and executes a one-time Cloud Run job with zero retries and waits for completion. Record the job execution ID and result. Never run `db:migrate` or the demo seed on production.
10. After DEV4952's separate production bootstrap command is available, run `bash infra/gcp/prepare.sh bootstrap-secrets`. Enter two distinct passwords from a password manager; the terminal does not echo them. Run `bootstrap-grants`, then `bash infra/gcp/release.sh bootstrap SHA`. Verify account/asset counts without credentials, run `bootstrap-revoke`, and delete the one-time job after retaining its redacted execution evidence. The runtime service account never receives bootstrap-password access.
11. Run `bash infra/gcp/release.sh deploy SHA`. It deploys the immutable app digest as a **private** Cloud Run service with Direct VPC egress and Cloud SQL attachment. Because the service URL is unknown on first creation, it initially uses a harmless placeholder origin, reads the actual HTTPS URL, then updates `APP_ORIGIN` to that URL. Both revisions remain private during this process.
12. Run `bash infra/gcp/verify.sh private`. Verify the ready revision, frontend, process health, and database readiness. Then, after approval to publish, run `bash infra/gcp/release.sh publish`. This checks the private service, grants public invoke, and checks public HTTP endpoints.
13. In a browser, use the uniquely provisioned accounts to test login, session restoration after refresh, catalog read, borrow request, custodian checkout, and persistence across a new revision. Record statuses, counts, and redacted screenshots only. The automated HTTP check does not establish these browser results.

For rollback, identify a previous compatible revision and run `bash infra/gcp/release.sh rollback REVISION`. It shifts traffic and reruns public HTTP checks. It **does not** undo a database migration. Keep migrations backward compatible with the preceding app revision; use a reviewed restore plan if data repair is required. First deployment has no earlier revision to roll back to.

## Evidence and troubleshooting

Record the source SHA, Cloud Build ID/status, two image digests, Cloud SQL instance state and private connection name, migration execution/status, Cloud Run revision and HTTPS URL, `/`, `/api/health`, `/api/ready` HTTP statuses, browser workflow, persistence after revision replacement, backup setting, IAM review, cost/budget check, and any failed step. Keep evidence under `docs/labs/lab-05/` or the PR, with no expanded Compose config, database URL, passwords, access tokens, cookies, CSRF headers, or raw secret values. If readiness fails, inspect Cloud Run revision logs and migration status before publishing. If a build fails, retain the Cloud Build ID and inspect its step logs. Do not retry migration blindly after partial success.
