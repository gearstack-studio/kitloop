# KitLoop

KitLoop is a web-based technology equipment inventory and borrowing system. The current Sprint 1 increment includes seeded Borrower/Custodian sign-in, protected catalog and request views, scoped checkout, and persistent loans. Return, search, reporting, and full inventory administration are scheduled later; see `docs/sprints/plan.md` for the draft plan and its allocation conflict.

## Local setup

Prerequisites: Node.js, npm, and PostgreSQL. From `server/`, install dependencies with `npm ci`, copy `.env.example` to `.env`, and set `DATABASE_URL`, `SESSION_CSRF_SECRET` (at least 32 characters), `DEMO_BORROWER_PASSWORD`, and `DEMO_CUSTODIAN_PASSWORD`. Use local synthetic credentials and keep `.env` out of version control. Set `APP_ORIGIN` to the client origin (default `http://localhost:5173`); `PORT` defaults to 3000 and `SESSION_TTL_HOURS` defaults to 12. The API requires the configured Origin for state-changing requests. In production, serve the client and API over HTTPS so the session cookie uses `Secure`.

Run `npx prisma generate`, `npm run db:deploy`, and `npm run db:seed` from `server/`. The seed creates `borrower.demo`, `borrower.other`, `custodian.demo`, and `custodian.other`, two synthetic assets, and distinct custodian assignments. Both Borrowers use `DEMO_BORROWER_PASSWORD`; both Custodians use `DEMO_CUSTODIAN_PASSWORD`. The seed is repeatable and stores salted password hashes. **Custodian scope (BR-05):** each Custodian sees and checks out requests only for assigned assets. `custodian.demo` manages the cameras (`KL-CAM-001`, and `KL-CAM-002` once the current seed has run); `custodian.other` manages the laptop (`KL-LAP-001`). A request for `KL-LAP-001` therefore appears only in `custodian.other`'s queue, not `custodian.demo`'s. Start the API with `npm run dev`.

From `client/`, run `npm ci` and `npm run dev`. The UI targets `http://localhost:3000` by default; set `VITE_API_BASE_URL` if the API uses another origin. The browser uses an HttpOnly session cookie and an `X-CSRF-Token` header supplied by login or `/api/auth/me`. The token stays in memory and is restored after refresh through `/me`. Borrowers can select an available item in the catalog and submit through `/requests`, where their request history is shown. Only one pending request per borrower/asset is allowed; different borrowers may still request the same available item without reserving it. See [FEAT-03](docs/sprints/sprint-1/FEAT-03-borrow-request-workflow.md) for API behavior and the migration duplicate-data preflight.

## Verification

Create a separate PostgreSQL test database with `test` in its name. From `server/`, copy `.env.test.example` to `.env.test` and set its test `DATABASE_URL`, `APP_ORIGIN`, and a distinct test `SESSION_CSRF_SECRET` of at least 32 characters. Apply migrations to that database with `npm run db:deploy` while `DATABASE_URL` points to the test database. `npm test` loads `.env.test` and rejects a database name without `test`; it must never target the development or production database. The integration suite creates and removes its own synthetic fixtures. Run `npm run build` in `server/`, and `npm run build` plus `npm run lint` in `client/`.

**Browser end-to-end tests (Playwright).** From `e2e/`, run `npm ci`, `npm run install:browsers`, then `npm run test:e2e`. The suite creates its own throwaway database (`kitloop_e2e_pw`) using the connection details in `server/.env.test`, runs its own API (`:3100`) and Vite (`:5174`) servers, and never touches the development or test database or your running dev servers. See [e2e/README.md](e2e/README.md) for isolation rules, options, outputs and limitations.

Run `npm test` from `client/` for the request form/history and mocked-HTTP app workflow tests (jsdom). These do not require a database; server integration tests do. The session token is random and only its SHA-256 hash is stored in PostgreSQL. Logout deletes the current session; expiration is checked on every protected request. All protected domain routes validate the session and server-derived role. Borrower record reads and Custodian record reads use owner/asset-assignment filters in database queries. See `docs/sprints/sprint-1/FEAT-01-authentication.md` for the versioned contract, acceptance criteria, and test evidence.

Custodians check out scoped pending requests using a future due date. Checkout atomically changes the request to `CHECKED_OUT`, creates one active loan, and makes the asset unavailable. Loan responses expose derived `ACTIVE`/`RETURNED` status. The [FEAT-04 contract](docs/sprints/sprint-1/FEAT-04-custodian-checkout.md) documents row locking, conflict behavior, tests, and the coordinated migration from the old `FULFILLED` request label. Stop the old API and deploy matching generated Prisma/client/API versions when applying that enum migration; existing history is preserved.
